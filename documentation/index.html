1. Install locally

Use Node.js 24 LTS, npm, and a local writable disk. The database is SQLite in WAL mode. No external database server is needed. One application instance owns the database. Windows, macOS, and Linux can run Node; the supplied Docker deployment targets Linux.

  1. Extract the buyer ZIP into a dedicated folder. Open a terminal in that folder.
  2. Run node --version. Install Node 24 LTS if necessary. Then run npm ci.
  3. Copy .env.example to .env. Set APP_URL=http://localhost:3000 for local use. Never put real secrets in a public repository.
  4. Run npm run build. This checks all application and test TypeScript, compiles CSS and React, and bundles the server and administrative commands.
  5. Temporarily set ADMIN_EMAIL, ADMIN_NAME, and ADMIN_PASSWORD in .env. Use your email and a unique password of 12–128 characters. Run npm run admin:create. Remove the password from the file after creation. The command refuses to overwrite an existing account.
  6. Run npm start. Visit localhost:3000 for the store and localhost:3000/admin for administration. Use npm run dev when changing source code.

There is no shared default administrator login, fake catalog, or seeded financial history. The store starts empty. Public registration always creates a customer account.

2. Set up and operate the store

  1. Settings: set your store name, domestic selling country, currency, flat shipping charge, tax rate, support email, and business address. USD is the default. USD, EUR, GBP, CAD, AUD, INR, SGD and AED are supported. Amounts are stored as integer minor units. Currency cannot change after orders or savings enrollments exist; create another store for another currency.
  2. Products: publish title, unique SKU, category, description, price, available stock, warranty months and an optional HTTPS image URL. A warranty of zero means none. Use only images you own or can license. Unpublish using the product editor; existing order snapshots remain intact.
  3. Orders: inspect totals, delivery addresses and history. Only confirmed payments enter fulfillment. Move paid orders to processing, then shipped with carrier/tracking details, then delivered. Download actual PDF records. If using Shippo, request rates using parcel dimensions in centimeters and weight in kilograms, then explicitly purchase a label.
  4. Refunds: request a full refund from the order screen. The provider controls settlement status. Credited orders return their savings credit. Returned physical inventory must be inspected and manually added back to available stock; a refund does not automatically restock a shipped item.
  5. Customers: inspect customer verification and disable access if necessary. Disabling revokes active sessions. This dashboard does not expose password hashes or provider secrets.
  6. Vouchers: specify a discount, minimum spend, maximum uses and expiry. Reservations consume availability and cancellation restores it. Disable unused promotions as needed.
  7. Savings: create an immutable monthly plan with term, maturity bonus and explicit terms. Retire plans to prevent new enrollment; existing plans keep their agreed financial parameters.
  8. Support inbox: answer customer conversations and warranty claims. For trade-ins, quote a value, wait for customer acceptance, and mark received only after inspection. A personal voucher is issued once and is restricted to that customer.
  9. Audit history: inspect recent account, product, financial and staff activity. Store timestamps are UTC.

The overview displays recorded figures only. No sales, ratings, shipping estimates, verification results or customer activity are fabricated.

3. Configure real external services

Credentials belong in the server environment or your deployment secret manager. Restart the server after changing them. “Configured” in the dashboard means credentials are present; it is not a provider health certification. Complete each provider's sandbox checks before using live keys.

Stripe payments and refunds

Set STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET, and the public HTTPS APP_URL. Configure the webhook destination https://your-domain/api/webhooks/stripe. Start with Stripe test mode. Subscribe to:

checkout.session.completed
checkout.session.async_payment_succeeded
checkout.session.async_payment_failed
checkout.session.expired
refund.created
refund.updated
refund.failed
invoice.payment_succeeded
customer.subscription.deleted
identity.verification_session.verified
identity.verification_session.requires_input
identity.verification_session.processing
identity.verification_session.canceled

The server verifies webhook signatures against the raw request body and deduplicates event IDs. Order amount, currency, checkout identity and payment state must match. A browser redirect cannot mark an order paid. Stripe Checkout handles payment details directly. Enable supported payment methods in your Stripe account; financing/BNPL availability depends on country, currency and Stripe eligibility, not a promise of 0% financing from this app.

For local sandbox forwarding, use the official Stripe CLI and its printed webhook signing secret. Keep the application origin set to the exact URL you open. Follow Stripe fulfillment guidance and webhook setup.

Recurring savings and identity

Customers must verify phone and identity before enrollment. Stripe-hosted recurring Checkout authorizes payments. Confirmed invoices create installments; completing the term creates store credit plus the agreed bonus. Recurring payment cancellation is scheduled for the plan term. Customers can request unused principal back to the original payment methods; bonus credit is forfeited. Credit already spent or reserved in an order cannot be withdrawn. Payment and refund callbacks may arrive asynchronously.

Enable Stripe Identity on your account. Customers upload documents on Stripe's hosted page; the application stores verification identifiers/status, not document scans. See Stripe Identity. This is identity verification, not credit-bureau assessment. Buyers must confirm their savings model and business are supported by their provider and selling jurisdiction before publishing a plan.

Twilio Verify

Set TWILIO_ACCOUNT_SID, TWILIO_AUTH_TOKEN, and TWILIO_VERIFY_SERVICE_SID. Create an SMS Verify service and enable the intended destinations. Customers enter international E.164 numbers such as +12025550123. The backend checks Twilio's approved result before updating the account. No OTP is returned to the browser or logged. See Twilio Verify.

Shippo

Set SHIPPO_TOKEN and SHIP_FROM_ADDRESS, a JSON address object with name, street1, city, state, zip, country, phone, email. Use an address accepted by your carrier and a Shippo test token first. Rates are stored against the order and expire after 30 minutes. Label purchase uses one recorded request per order to avoid blind duplicate purchases. See Shippo test/live modes.

If a label request times out after reaching the provider, inspect that order's metadata in Shippo before doing anything else. An uncertain request is retained rather than automatically repurchased. Record an externally purchased label through the order's manual tracking controls; do not blindly retry charges.

SMTP password recovery

Set SMTP_HOST, SMTP_PORT (usually 587), SMTP_SECURE (true for implicit TLS, usually port 465), SMTP_USER, SMTP_PASSWORD, and SMTP_FROM. Use an authorized sender domain. Recovery links expire in 15 minutes, are stored hashed, can be used once, and revoke existing sessions. The public response does not disclose whether an email is registered. Configure SPF/DKIM with your mail provider and verify delivery. Account recovery does not silently fall back to showing tokens.

4. Customer workflows

Browse and search the published catalog, register an account, and add products to the persistent cart. Enter a delivery address, optional voucher and available savings credit. The server recalculates prices, quantities, tax, discounts and stock. An order is initially unpaid unless fully covered by matured credit. Use Pay securely to enter the payment provider's hosted checkout, then refresh Orders to see confirmed status.

Download order PDFs and eligible warranty certificates from the account. Use Support to contact staff, submit a claim using its warranty reference, or request a trade-in valuation. Track shipments through actual carrier details. Phone and identity verification are available from Account when configured. Profile/password updates persist; sign-out revokes the session.

5. Deploy with Docker and HTTPS

Use a Linux server with Docker Compose, a persistent local disk, a domain and TLS reverse proxy. Run one application container per store/database. The database volume must survive deployments.

docker compose build
docker compose up -d
docker compose exec app node dist/scripts/create-admin.mjs

Before creating the administrator, temporarily supply its environment credentials to the container. Remove them afterward and recreate the container. Set APP_URL=https://your-domain. The supplied Compose file exposes the app only on 127.0.0.1:3000. Install Caddy on the host and replace the example domain in deployment/Caddyfile with your domain. Point DNS to the server. Caddy handles HTTPS and proxies to the local port. TRUST_PROXY=1 is appropriate only when the app is reachable through exactly this trusted proxy.

The application sets secure HttpOnly session cookies in production. Use localhost for local production testing or HTTPS for a public origin. Do not expose the development server publicly. CSP, origin checks, CSRF tokens, prepared SQL statements, session revocation and rate limits are included, but infrastructure hardening and ongoing updates remain operational responsibilities.

For non-Docker deployment: use Node 24, run npm ci, build, then npm ci --omit=dev and npm start. The bundled production server loads without Vite or tsx. A process supervisor should restart the service after failures. Keep dist, documentation, package files, scripts/start.mjs, runtime dependencies and the persistent data directory together.

Run maintenance every five minutes (for example with cron or Task Scheduler):

docker compose exec -T app node dist/scripts/maintenance.mjs

Unused reservations without a payment session expire after 30 minutes. Started Stripe sessions are released by verified expiry/failure callbacks; delayed payments must not have their inventory released just because a local timer elapsed. Monitor undelivered Stripe events and unresolved payment/label/refund requests.

6. Back up and restore

Run npm run backup or the equivalent Docker command below. It uses SQLite's backup API to produce a consistent snapshot including committed WAL data. Set BACKUP_DIRECTORY to choose a destination.

docker compose exec -T app node dist/scripts/backup.mjs

Schedule daily backups and copy snapshots to encrypted off-server storage with retention. Back up before every application update. Backups contain customer data; restrict access and protect keys separately. Test a restore before relying on the procedure.

  1. Stop the application and any maintenance job.
  2. Keep an additional copy of the current database and its sidecar files.
  3. Restore a chosen snapshot as the configured DATABASE_PATH in a fresh data directory. Do not leave stale -wal/-shm files next to the restored database.
  4. Check SQLite integrity, start the application against the restored copy, and confirm accounts, orders and balances.
  5. Replay/reconcile provider events that occurred after the snapshot before accepting further payments. Never test a restore with live webhook traffic connected to an old database.

Database migrations are recorded and run on startup. They do not reset customer data or seed demonstration sales.

8. Verify installation and upgrades

npm run build
npm test
npx playwright install chromium
npm run test:e2e
npm audit

API tests use temporary or in-memory SQLite and provider doubles confined to test files. Browser tests launch an isolated server with a test-only administrator and no real charges. They do not alter the running store. Test screenshots and traces are written under test-results and excluded from the buyer package. Never copy test fixture accounts into production.

Before launch, verify live configuration using provider sandboxes: payment success/decline/expiry/delay, duplicate callbacks, full refunds, phone code failure/expiry, Identity completion, recurring term end, savings withdrawal, credit redemption and carrier label purchase. Check SMTP delivery, HTTPS, session revocation, mobile keyboards, focus/zoom, stock conflicts, and recovery after restart. Follow RELEASE_CHECKLIST.md; automated passing results do not replace these checks.

Troubleshooting

  • 503 provider unavailable: complete the corresponding environment settings and restart. This is deliberate; the app does not fake success.
  • 403 request token/origin: reload, sign in again, and ensure APP_URL exactly matches your browser origin. Do not alternate localhost and 127.0.0.1.
  • 401 after login on a public HTTP site: use HTTPS; production sessions require secure cookies.
  • Order pending after payment: inspect Stripe webhook delivery and signing secret. Do not manually mark the order paid.
  • Cannot change currency: existing financial records lock the currency. Use another store database for a different currency.
  • SQLite lock/permission failure: use a writable local persistent directory, one app instance, and correct file ownership. Do not put the database on a network share.
  • Build runtime errors: verify Node 24, reinstall with npm ci, and inspect the reported type errors. The system Node runtime may differ from the project-local development runtime.
  • Refund/label uncertain: reconcile the provider record before initiating another transaction. Do not delete financial history to clear an error.

9. Product scope and release responsibility

This release targets a single store on a single persistent server. It has one selected currency and delivery country, flat tax/shipping settings, fixed monthly savings plans, full-order refunds, and staff-managed fulfillment/support. It does not claim marketplace multivendor operation, multiwarehouse inventory, automatic international tax calculation, partial refunds, a credit-bureau service, a GPS courier fleet, guaranteed bank approval or a general AI assistant.

Third-party account approval, provider fees, real catalog assets, shipping/tax policy, financial eligibility, production hosting and marketplace author approval are supplied by the buyer/owner. The local release checks do not certify Envato acceptance. Review current Envato requirements, including author intake and AI-content rules, before submission. Public documentation is served at /documentation/ without a purchase-key gate.

The distributed application uses code-based styling, a text brand mark, and system fonts. It includes no archived Google-hosted prototype images or demonstration customer identities. The buyer supplies product imagery and must keep commercial/redistribution permissions as applicable.

Third-party package licenses and exact installed versions are included in THIRD_PARTY_NOTICES.md and the accompanying licenses/ directory in the distribution. These notices do not grant permission to third-party catalog images or promise marketplace eligibility. Preserve required notices when redistributing.
